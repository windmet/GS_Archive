# 门户冷加载性能基线（L3）

日期：2026-10-13。计划见 [门户静态化路线](GS_ARCHIVE_PORTAL_STATIC_ROUTE_PLAN_20261012.md) §5。被测对象：**正式站** <https://gs-archive-preview.pages.dev>（部署 `6ba4c547`，入口 `index-Cd_pUXAO.js`），不含本分支的 L1/L2 改动，所以偶像/Unit 页用的是 `?view=` 旧地址。

## 方法

`node scripts/measure-portal-cold-load.mjs <label> --runs=N --profile=mobile|desktop`

- 每次运行新建浏览器 profile，禁用缓存（冷加载）。浏览器为本机缓存的 Playwright Chromium headless，原生 CDP。
- mobile 档 = Lighthouse 移动端预设：390×844、DPR 3、RTT 150 ms、下行 1.6 Mbps、上行 750 kbps、CPU 4 倍降速。desktop 档：1350×940，不降速。网络之上还叠加了本机到 Cloudflare 的真实网络。
- “实体出现”= 页面自己的内容第一次出现在 DOM 的时刻（偶像页：偶像名与关联入口；Unit 页：成员列表；目录页：卡片与 SSR 标签）。FCP 可能只是空外壳，这个指标才是读者真正在等的。首页的判定比较宽松（出现 canvas 或偶像名即算），只作参考。
- 结果取中位数；mobile 每页 5 次（首页有 1 次因浏览器启动失败缺失，脚本之后已加重试），desktop 每页 3 次。原始数据：`.analysis/perf-baseline/production-mobile-20261013/`、`production-desktop-20261013/`。

## 观察（只写测到的）

1. **JavaScript 不是主要耗时。** 入口包压缩传输约 190 KB，各页脚本合计 189–247 KiB；手机档（4 倍 CPU 降速）下脚本执行 255–308 ms，长任务合计 0.6–1.0 s。
2. **首屏慢在串行的网络往返。** 手机档 FCP 2.4–3.6 s，而 TTFB 只有 0.4–1.0 s。从代码看，路由要等页面代码块与 read-model 数据都准备好才提交渲染（`prepareArchiveRoute`），所以一次冷加载是 HTML → 入口 JS → 路由代码块 → read-model JSON → 渲染的串行链。偶像页的内容要到 5.5 s 才出现，FCP 与内容出现之间还隔着约 2 s。
3. **波动大。** 正式站偶像页手机档 5 次的内容出现时间在 4.1–9.2 s 之间，主要来自真实网络。框架/渲染方案的对比因此放在本地生产包上做（L4），网络只由限速模拟。
4. **字节大头是图片。** Portal 手机档 3.3 MB 中约 2.9 MB 是图片，桌面 5.3 MB 中约 4.9 MB。
5. **Portal 存在明显的布局偏移**：手机 CLS 0.679，桌面 0.365，远超 0.1 的常用阈值。这与渲染框架无关，可以单独修。

## 对决策门的含义

- Astro 的核心卖点是“少发/少执行 JS”。本基线显示 JS 执行并非瓶颈，这条收益在 GS Archive 上空间有限。
- 能直接缩短等待的是“首个 HTML 就带上实体内容”，也就是 L4 的 A/B 组要验证的东西。

## 限制

- 模拟手机，不是真机；headless Chromium 用软件渲染。
- 未测 INP（需要交互）；Home 的判定较宽松。
- 待用户执行：iPhone 与 Android 真机各测偶像详情、Home 两页（步骤见计划 §2.5），每页 3 次取中位数。
