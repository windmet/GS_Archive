# 开发文档撰写流程（2026-11-03）

开发手记、架构总论、视频脚本，都按同一条流程写。原则只有一条：**每个日期和数字都能追到证据**。
时间线核对的结果见 [01_TIMELINE_EVIDENCE.md](01_TIMELINE_EVIDENCE.md)。

## 1. 三份文档，三种读者

| 文档 | 读者 | 口吻 | 主要素材 |
|---|---|---|---|
| 站长的话 / 开发手记 | 制作人、路人、视频观众 | 第一人称，站长自己的话 | 语音自述（Gemini 第 1、2 轮整理稿） |
| 架构总论 `OVERVIEW` | 技术同好、想做类似站的人 | 说明文，少形容词 | 仓库文档、PR、当前代码 |
| 决策登记册 | 以后接手的人和 AI agent | 条目式：当时怎么做、为什么改、现在的规则 | 交接文档、审计、验收文档 |

一段内容只放进一份文档，其他地方用链接引用，不复制。

## 2. 素材分级

| 级别 | 来源 | 怎么用 |
|---|---|---|
| A | Git 提交、PR、tag；当前代码 | 直接引用，写上哈希或 PR 编号 |
| B | 当天落地的仓库文档（`web_viewer/docs`、`notes`、交接） | 引用时写文件名；文档里的数字要和它写下的那天对应 |
| C | 站长回忆、语音自述 | 写感受和动机可以直接用；日期和数字要用 A/B 核对 |
| D | AI 整理稿（Gemini、Claude、GPT 的总结） | 只当线索。里面的数字和日期全部重新核对，形容词全部删掉重写 |

已经发现的 D 级错误：把 11th LIVE DAY2 写成 9-11（实为 9-13）；PR #48 写成 105 个提交（实为 108）；
「果蔬」被当成语音识别错误（其实是 GS 的昵称）；48,268 等三个数字在仓库里找不到出处。

## 3. 七步流程

1. **采集**：语音自述和 AI 整理稿原样存到 `web_viewer/.analysis/devnotes-sources/`（被 Git 忽略，仓库是公开的）；仓库文档直接写路径引用。
2. **对时间**：每个时间点进时间线表，标 ✓ / ⚠ / ？。⚠ 写清是哪边不一致，？列进「需要站长补充」。
3. **定大纲**：先写每章的「一句话论点」和要用的证据编号，再动笔。
4. **写初稿**：开发手记由站长口述，再整理成文；总论和登记册可以由 AI 起草，但只能用第 2 步核过的事实。
5. **核事实**：逐句过一遍。日期、数字、模型名、PR 编号必须能在时间线或仓库里找到；找不到就删掉，或者标「待复测」。
6. **站长审阅**：口吻、称呼、要不要公开的细节（朋友署名、工具账号、额度花费）由站长决定。
7. **发布与维护**：发布到开发文档站。之后每合并一个重要 PR，在开发日志追加一条（日期 + PR + 一句话）；每月整理一次，写进总论。

## 4. 文体规则

- 写事实，不写评价：「单曲读取从 43.58 MB 降到 1.79 MB」，不写「教科书级」「像素级」「极其硬核」。
- 模型和工具按 commit trailer 与交接文档的写法统一：DeepSeek、Codex、ChatGPT、Claude Code、Claude Opus 5.5、Gemini（AI Studio）。语音里的「露娜」「Astra」先和站长确认再写。
- 站长自述保留口语和自嘲，只改错字，不替站长加感慨。
- 「果蔬」第一次出现时写「果蔬（GROWING STARS 的昵称）」。
- 不确定的就写不确定：「约」「据回忆」「未复测」。

## 5. 不公开的内容

开发文档站是公开的，下面这些不写：

- 解密密钥、解包与提取资源的具体步骤和脚本参数。
- 资源包和 IPA 的来源链接、提供者。
- 能直接拿去还原客户端的成套技术细节。

可以写：遇到了什么问题、思路、为什么这么取舍、结果。逆向部分只写到「读取了客户端的什么语义」，不写「怎么拿到」。
